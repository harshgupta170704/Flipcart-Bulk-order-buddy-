# Audit and plan: the ordering portal against the order-unit ledger spec

**Date**: 2026-10-24 · **Spec**: [spec.md](spec.md) · **Evidence**: [ui-evidence.md](ui-evidence.md)
**Method**: six independent read-only reviews of the code, one per story area, graded requirement by requirement with file:line references; a structural critic resolved contradictions between them and proposed the build order; a rendered-screen pass measured every page (controls, words, height). 910 backend tests pass at the starting point.

|---|---|---|---|---|---|

| Ingestion — how units enter (FR-021–025, 060–061) | 0 | 3 | 3 | 4 | Units enter only by the tool's own runs and by signing in to scrape; no report or PDF upload exists |

| Sign-in and organizations (P6) | 2 | 4 | 6 | 0 | One admin login from config; no users, roles, organizations or password reset |

**Already met**: FR-051, FR-053, FR-056, NFR-001, NFR-010 (and NFR-002/NFR-003's spirit — no card data is stored; platform passwords are never stored, only OTP-login sessions).

**Live bugs found by the audit** (fix first, decision-neutral):
- `OrderOut` omits 11 columns, including every synced field, so the "sync columns" view can never show data and the "read back from Flipkart" note is always wrong (`backend/app/schemas/order.py:35-49`).
- "Delivered"/"cancelled" are classified in three places with two different meanings (`automation/sync.py:46-57`, `core/alerts.py:65`, `components/OrderTable.tsx:175-181`); any dashboard count built on them would disagree with the table.
- The Invoice "Open" link points at a Flipkart URL that needs that account's session, which the operator's browser does not have — a dead link.
- The dashboard's own copy promises an "address mismatch" alert that no rule raises.
- No one-at-a-time guard on jobs server-side: a second tab can start a second sync.
- Export ignores the filter and dumps every order; the page says otherwise.

## 6. Speed

**Per order (automation)** — done today: 23 s → 14 s to the final button; of what remains, ~9 s is deliberate safety (clickability wait, price-settling window) and the rest is Flipkart's page loads. Further trimming waits for a few real orders to show Flipkart's confirmation timing; the volume lever is `max_concurrency`, bounded by Flipkart's own limits, not by the code. **26 Oct 2026:** the run now records when it begins and ends work on each account (`JobItem.started_at` / `finished_at`), so from the next real run the per-order time is read off the run history instead of measured by hand.

**Portal (this plan)** — the critic's finding is that speed is currently asserted, not measured. Phase 1 adds the measurement and the indexes; Phase 2 replaces the in-memory export of every order with a streamed, filtered one and stops the Ordering page fetching 500 accounts twice on mount; Phase 3 makes ingestion a file parse instead of a browser navigation per order; the UI splits its ten statically imported pages into route chunks. Target per C-12: a filtered ledger page in under 2 s at the 95th percentile with a year of units loaded — verified by the Phase 1 harness, not by feel.

## 7. Risks

- **C-1 undecided forks ingestion, invoices and address alerts** — each has a sign-in design and an upload design. Phases 1–2 are decision-neutral; D-a must be answered before Phase 3 starts.
- **Grain change** — unit limits SUM over `Order.qty`, six alert keys are per order id, settle and stats assume one row per order. D-b option 2 leaves Order untouched; a backfill script and a dual-read period cover the switch.
- **Unknown input formats** — no report sample and no invoice PDF exists in the repo; XLSX numeric cells lose digits past 15–16, so Unit IDs saved as numbers are already damaged on the way in. Parsers are built against real samples only.
- **Large files and storage** — no volume, ephemeral AWS disks, downloads buffered into memory in the browser, nginx default buffering, and a log redactor that blanks any 12+ digit run (it would blank IMEIs and unit ids in job messages).
- **No frontend test runner** — the Ordering/OrderForm/OrderTable split in Phase 2 moves 1,300 lines of UI with only the backend suite as a net; smoke tests come first in that phase.
