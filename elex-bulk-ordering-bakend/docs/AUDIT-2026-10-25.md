# Audit of the Flipkart Ordering Suite — 25 Oct 2026

**Scope.** A static read of `backend/app`, `frontend/src`, the docs, the compose
stack and the laptop's local setup, as the tree stood on the evening of
25 Oct 2026. The backend suite was run against a throwaway database
(1,352 passed, 1 failed — see F-34); the frontend type-check is clean and its
83 tests pass. Six automated audit lenses (authentication, authorisation,
card data, the ordering flow, input validation, invoice files) ran to
completion; the twelve others were refused by the account's usage limit, so
those areas (job engine, database, OTP/login, read-back, alerts and limits,
frontend, deployment, CLI, docs, tests, performance) were read by hand. The
three-verifier pass planned for every finding could not run; instead each
finding below was re-checked against the code by hand before it was kept, and
anything that did not survive is listed under "Not confirmed".

**Nothing was changed.** No file under `ordering/` was modified, no browser was
launched, no order was placed.

Severity: **critical** = money loss or card/credential exposure on a path that
runs today; **high** = serious failure on a real path, or sensitive data in
the wrong place with a precondition; **medium** = limited blast radius or an
unlikely precondition; **low** = hygiene, docs, minor.

## Findings

### Critical

#### F-1 · Card run presses "Pay" even when the card form was never filled
**Where.** `app/automation/ordering.py`: `_enter_card` (catches every fill failure, logs, returns `None`), `run_order` (calls `_enter_card`, then `read_final_amount`, then `_submit_and_confirm` with no check that the card was entered), `_submit_card` (presses the first `Pay ₹…` button). The card selectors — `PAY_OPTION_CARD` (`span.QbbOLN` with the text "Credit / Debit / ATM Card"), `CARD_NUMBER` (`#cc-input`), `CARD_EXPIRY` (placeholder `MM / YY`), `CARD_CVV` (`#cvv-input`) — sit in `selectors.py` under "Payment (legacy; card form below still valid)" and, unlike the COD controls, carry no "CONFIRMED live" note. No card run has been made (ROADMAP §1).
**What is wrong.** A card run that cannot find or fill the card form still reaches the pay step and presses Pay. What Flipkart then does depends on what its payment page has preselected — nothing (a validation error), or a saved card / other instrument the account already holds.
**Why it matters.** The first real card run is imminent (the owner's corporate card sheet). If the legacy selectors are dead, every account reaches "Pay" with an empty form; the best case is 5,000 "unconfirmed" rows, the worst case is a charge on an instrument the operator did not choose. The COD path has the opposite discipline (refuse unless exactly one "Confirm order" button).
**Fix.** Make `_enter_card` return a verdict, and refuse (`failed`, "card could not be entered — nothing was charged") unless all three fields were filled and the chosen method is still the card option; map the card selectors live in a headed browser before the first card run; refuse when more than one "Pay" button matches, as `_submit_cod` does.

#### F-2 · Card number, expiry and CVV can be written to the application log
**Where.** `ordering.py` `_enter_card`: `log.error("_enter_card failed: %s", exc)`. The installed driver (Playwright 1.64.1, `driver/package/lib/coreBundle.js`) logs ``  fill("<value>")`` into the action's call log, and the Python client appends `"\nCall log:\n…"` to the error message (`playwright/_impl/_connection.py`). The worker in `tasks.py` redacts its own messages with `_redact` (12+ digits), but this line is logged inside the flow, unredacted.
**What is wrong.** When a card field resolves but the fill times out or fails, the error text carries the literal value typed — the PAN, the `MM/YY`, the CVV — and it goes to stderr, i.e. the container log.
**Why it matters.** Card data in logs is the one place the owner's decision did not allow; logs are kept, shipped and read by more people than the database. The same mechanism exposes the OTP code typed in `_enter_otp` and the address fields.
**Fix.** Never log the raw exception from a fill of a sensitive value: log `type(exc).__name__` plus the selector; run every log line from `ordering.py` through the same `_redact` (and extend it to 3–4 digit CVV/expiry patterns when the message came from a card step).

#### F-3 · Failure screenshots capture the payment page with the card number on it; the folder is unprotected and not git-ignored
**Where.** `tasks.py` `run_order_job` worker: on `status == failed` it calls `_snapshot(page, f"failed-account{account_id}")`; `ordering.py` `_submit_and_confirm` calls `_snapshot(page, "unconfirmed")`. `_snapshot` takes a `full_page=True` screenshot into `backend/diagnostics/`. `.gitignore` does not list the folder (`git check-ignore` returns nothing); the four PNGs there today show the checkout with the account's name, address, phone, GSTIN and business name.
**What is wrong.** On a card run, the common failures after `_enter_card` (unreadable total, no Pay button, no confirmation) screenshot the payment page with the card number and expiry in the form fields, in clear, on disk, for ever (no retention).
**Why it matters.** DEPLOY.md promises "nothing is written to disk"; a commit, a backup or a screen share leaks card and customer data.
**Fix.** Skip the screenshot on card runs once `_enter_card` has run, or blank the card inputs (`page.fill` with an empty value) before it; add `backend/diagnostics/`, `backend/backups/` and `accounts-recovered.xlsx` to `.gitignore`; delete screenshots older than N days; document the folder as sensitive.

### High

#### F-4 · The GST step at checkout does nothing, and the ledger records the GST as billed anyway
**Where.** `ordering.py` `fill_gst` clicks `GST_EXPAND_BTN = //button[@class="dSM5Ub VO3vnd"]`, fills `GST_GSTIN`/`GST_BUSINESS`, clicks `GST_SUBMIT`, and catches every exception with `log.error`. `selectors.py` ("The REAL checkout flow, mapped live 2026-10-23") states that `/viewcheckout` has no `<button>` elements at all. `tasks.py` `_order_columns` writes `gst_name`/`gstin` from the run's chosen GST whatever happened on the page.
**What is wrong.** The order is billed under whatever GST the Flipkart account already carries (the checkout screenshot shows "GST Invoice … Change" preset at account level), and the ledger says it was billed under the run's GST.
**Why it matters.** An order invoiced to the wrong entity succeeds silently; input tax credit goes to the wrong GSTIN. The live orders so far happened to carry the right GST because the account already had it saved. The `gst_mismatch` alert (built 26 Oct) catches it only after a read-back.
**Fix.** Map the checkout's "GST Invoice / Change" control live; make `fill_gst` return whether the page now shows the wanted GSTIN and refuse the order when it does not (as `ensure_delivery_address` does for the address); write `Order.gstin` only from what the page showed.

#### F-5 · No bank OTP / 3-D Secure step on the card path
**Where.** `ordering.py` `_submit_card` then `await_order_confirmation` (waits up to `ORDER_CONFIRMATION_TIMEOUT_MS = 90_000` for `/orderresponse`). The legacy `bank_otp_fill_wait = 300` setting exists in `config.py` and is used nowhere. PLAN.md §5 assumes "corporate cards need no payment OTP".
**What is wrong.** Indian card-not-present payments are routed to the issuing bank's authentication page; nothing in the flow handles it, so the order is recorded `unconfirmed` (with the card number, per the owner's rule) and the operator checks the account by hand.
**Why it matters.** The card mode is marked "Have" in ROADMAP §1 but has not been exercised; the first run may produce nothing but unconfirmed rows and critical alerts.
**Fix.** Run the first card run on one account with the browser visible and watch what the bank shows; decide whether the OTP can be read (SMS/mail) or the run must pause for a person; until then mark card mode "untested" in the UI copy.

#### F-6 · The code exists only on this laptop
**Where.** `git log --oneline` in `ordering/` shows one "Initial commit"; `git status` lists `backend/`, `frontend/`, `docs/`, `docker-compose.yml`, `README.md` as untracked.
**Why it matters.** A disk failure, a careless `rm`, or an agent script rewriting files loses the tool; regressions cannot be bisected; the 25 Oct database wipe shows scripts do run beside the app.
**Fix.** Fix `.gitignore` first (F-3), then commit and push to a private remote; commit after each review round.

#### F-7 · A failed reservation write logs the card number
**Where.** `ordering.py` `_submit_and_confirm`: `log.error("could not record the order before sending it: %s — not sending", exc)`. The reservation (`tasks.py` `reserve_order` → `save_order_result`) inserts a row whose `card_number` is set (status `unconfirmed` is in `UNITS_SPENT_STATUSES`). `app/db/base.py` creates the engine without `hide_parameters=True`, so a `StatementError`'s text ends with `[parameters: {…, 'card_number': '4111…'}]`.
**Why it matters.** A "database is locked" on SQLite under a four-browser run, or any PostgreSQL error at that moment, puts the PAN in the log.
**Fix.** `create_engine(..., hide_parameters=True)`; log only the exception class on this path.

#### F-8 · A logged-out account reads back as a clean "0 orders seen"
**Where.** `sync.py` `scrape_orders`: when the orders list bounces to `/login` it logs an error and returns `[]`; `sync_tasks.py` worker then runs `_reconcile` on nothing and returns `_Outcome(True, "0 order(s) seen, 0 matched, …")`. The account's status stays `session_valid`, so the `session_invalid` alert rule (`alerts.py` `find_invalid_sessions`) never fires.
**Why it matters.** The read-back is what keeps delivery state, OTPs and the overdue alerts honest; a dead session silently stops all of it while every screen stays green.
**Fix.** Return a distinct outcome from `scrape_orders` (e.g. raise `NotSignedIn`), mark the account `session_invalid` and the item failed, and say so in the summary.

#### F-9 · An unconfirmed row can be settled onto the wrong order
**Where.** `sync_tasks.py` `_adopt_unconfirmed`: every unconfirmed, id-less row of the account is a candidate; `max(candidates, key=agreement)` picks the newest even when every score is 0. `_reconcile` calls it for the first unknown order in the recent list.
**What is wrong.** An unknown order in the account's recent list — the owner's own purchase, an older order within the 20-row window — gets filed as the unconfirmed order: status `placed`, the run's amount and product, someone else's order id.
**Why it matters.** The ledger then shows a placed ₹18k order that never happened, with a card number on it, and the real unconfirmed order (if it exists) is imported as a duplicate later.
**Fix.** Require a minimum agreement (model or amount) and an order date not earlier than the reservation; otherwise leave the row unconfirmed for a person to settle.

### Medium

#### F-10 · Quantity read-back failure records one unit
`ordering.py` `set_quantity`: after APPLY, if the `Qty:` box cannot be read within 4 s the function returns `QuantityOutcome(1, …)` and the order proceeds. If the checkout did apply N units, the order is placed for N and recorded as 1; the budget hands the other units to another account. **Fix:** fail closed — refuse the order when the applied quantity cannot be read.

#### F-11 · Address fallback can pin a generic location
`ordering.py` `address_search_queries` widens to `"<city> <pin>"` and then the bare pincode; `add_delivery_address` accepts any suggestion whose "Deliver To" block carries the right pincode and types only `line1, floor` into the house field. The saved address can be "Tower 5, 1005 · Lucknow 226013" pinned at a city centroid; `address_matches` then passes (name + pincode + line1) and the order ships to it. The 24 Oct Madiyanva mis-pin was this class of failure. **Fix:** require the chosen suggestion to share a locality word with the Address Book entry (or confirm the pin page's locality text against `area`/`line1`), and never fall back to the bare pincode without an operator-confirmed locality.

#### F-12 · Shared inbox: a concurrent login can get another account's OTP
`otp.py` `_search_ids`: `FROM "flipkart" TO "<address>"` first; when nothing matches it searches `FROM "flipkart"` alone — any recipient. With `ORDERING_MAX_CONCURRENCY` logins at once, account B's first poll (its own mail not yet arrived) finds A's fresh code, and `_fetch_code` returns it; `not_before` does not help because A's mail is newer than B's request. **Fix:** never return a code from the sender-only search when the mailbox is shared; or serialise logins per mailbox; or require the recipient header to match when any `TO` search is possible.

#### F-13 · Orders and coupons ignore the proxy
`tasks.py`: `run_login_job` passes `proxy=settings.proxy_server`; `run_coupon_job` and `run_order_job` call `browser_page(headless=…, cookies=cookies)` with no proxy. A session created through the proxy's IP is then used from the server's own IP, and the setting silently does nothing for the runs that matter. **Fix:** pass `proxy=` on every `browser_page` call (and check Playwright's `proxy` option takes credentials as `username`/`password`, not inside the URL).

#### F-14 · Product preview is a server-side browser anyone signed in can aim anywhere
`app/api/products.py`: the only check is that the URL starts with `http(s)`; a fresh Chromium is launched per uncached URL (cache 64 entries / 120 s). An operator can probe `http://db:5432`, `http://redis:6379` or any internal address and read the navigation error text, and can launch unbounded browsers. **Fix:** allow only `flipkart.com` hosts; serialise previews with a semaphore; strip the raw error.

#### F-15 · Proxy credentials echoed to operators
`app/core/app_settings.py` `SECRET_FIELDS = ("otp_imap_password",)`; `proxy_server` is documented as `http://user:pass@host:port` and comes back verbatim from `GET /settings` (any role). **Fix:** add `proxy_server` to `SECRET_FIELDS` (or mask the userinfo part).

#### F-16 · Backup ring erased by a burst of restarts
`app/db/base.py` `backup_sqlite`: a copy at every start when the file changed, newest `BACKUPS_KEPT = 10` kept. Today's ten copies are all from 21:06–21:57; nothing older survives. **Fix:** age tiers (e.g. one per day for 30 days plus the newest ten), and skip a copy when the last is younger than a few minutes.

#### F-17 · Stale secret in `backend/.env`
The commented `#ORDERING_OTP_IMAP_USER=` and `#ORDERING_OTP_IMAP_PASSWORD=` lines still hold an older mailbox and App Password. (Values deliberately not reproduced here.) **Fix:** delete the lines; revoke that App Password in the Google account.

#### F-18 · Compose and the "encrypted" claim
`docker-compose.yml`: `POSTGRES_PASSWORD: ordering` and the same string inside `ORDERING_DATABASE_URL`; no `restart:` on any service (a reboot leaves the stack down); `web` depends on `api` with no health condition; nothing terminates TLS although the app is internet-facing; DEPLOY.md's opening says the database volume and backups "are encrypted" — no mechanism exists in the repo. **Fix:** read the DB password from `.env` with `:?` like the JWT secret; `restart: unless-stopped`; an api healthcheck; a TLS proxy (Caddy/nginx+certbot) in the stack; a documented disk-encryption and encrypted-backup procedure for the VPS.

#### F-19 · More than one API process breaks the run bookkeeping
`recovery.py` `fail_orphaned_jobs` marks every queued/running in-process job failed at start-up (only arq-dispatched rows are spared); `api/jobs.py` `_refuse_if_active` and the in-process event bus assume one process. PLAN.md §10 says ordering throughput scales "by running more API replicas". **Fix:** document "exactly one API process" (and remove the replicas sentence), or record an owner id + heartbeat on running jobs and sweep only stale ones.

#### F-20 · Card filter in URLs and in a job payload
`api/orders.py` `parse_filter` takes `card` (up to 32 characters) as a GET query parameter on `/orders`, `/orders/export.csv`, `/orders/export`; uvicorn's and nginx's access logs record the query string, and the saved view keeps it. `api/invoices.py` `_raw_filter` copies it into the compile job's `Job.payload` and `CompiledArchive.filters`, which `Job` documents as card-free. **Fix:** cap the filter to the last four digits, or move it to a POST body; drop `card` from the recorded filters.

#### F-21 · The CLI `order` command is unguarded
`cli.py` `cmd_order`: without `--email` it orders on every account with a session (the comment says exactly this is how an unselected account once ordered — the default was kept); it checks no unit limit, no budget and no active run; the card and CVV are command-line arguments (shell history, `ps`). **Fix:** require `--email` (or `--all` explicitly); run the same allowance check as the job; read the card from a file or a prompt.

#### F-22 · Settle can create duplicate order ids
`api/orders.py` `settle_order` writes `payload.order_id` without checking another row carries it (`orders.order_id` is indexed, not unique); the id-sheet import refuses that case, and invoice matching and the read-back key on the id. **Fix:** refuse with a 409 when another order (any account) already has the id.

#### F-23 · A blank cap is "no cap"; the API accepts `qty <= 0` and `inf`
`OrderForm.tsx`: an empty Target is sent as `null`, which `within_target(amount, None)` reads as "always allowed"; the form shows an info box and does not block. `api/jobs.py` `start_order_job`: `qty: int = Form(1)` has no lower bound (`set_quantity` orders one unit for 0 or negative), `target: float | None = Form(None)` accepts `inf` (cap always passes) and `nan` (always refused). **Fix:** make the cap required, or demand an explicit "run with no cap" confirmation; `qty >= 1`; `target` finite and `> 0`.

#### F-24 · GSTIN validated by length only
`app/schemas/address.py` `Gstin` enforces 15 characters, no pattern, no upper-casing. The read-back's `_GSTIN_RE` knows the real shape. **Fix:** validate against the pattern and upper-case on write.

#### F-25 · `%` and `_` unescaped in search
`account_filter.py` `apply` (`Account.email.ilike(f"%{q}%")`) and `order_filter.py` `apply` (`Order.model.ilike`): a search for `_` or `%` matches everything while `is_empty()` reports a narrowed filter — including when the filter is the one that starts a run ("select all matching"). **Fix:** escape `%`, `_` and `\` and pass `escape="\\"`.

#### F-26 · Account import is too trusting
`io/excel.py` `import_accounts`: any non-blank text in the email column becomes an account; existing rows are matched with `Account.email == text` (case-sensitive) while the API lower-cases; `api/accounts.py` accepts `.xls`, which openpyxl cannot read, and echoes the raw exception. **Fix:** validate the address, lower-case before matching, accept `.xlsx` only, and report rows skipped.

#### F-27 · Upload buffering and unbounded PDF parsing
`api/invoices.py` `upload_invoices`: every file is `await file.read()` into `entries` before the 25 MB and 200-file checks; zips are unpacked in memory; `pdfplumber` runs with no page or time limit — in the API process that also runs the orders. **Fix:** read with a size ceiling, count members before unpacking, bound pages and wall-clock per PDF (or parse in a worker).

#### F-28 · Over-long parsed strings break PostgreSQL
`core/invoices.py` `apply_parse` assigns parser output straight to `String(64)/(255)` columns (`invoice_type` is a `' + '`-join of every fee title); `backfill_all` ends on the first exception and restarts from id 0, so one bad row starves every later one. SQLite stores it silently. **Fix:** clamp lengths; skip and record a failing row instead of aborting the pass.

#### F-29 · Missing headers; tokens in URLs
`frontend/nginx.conf` sets no `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy` or CSP (the JWT lives in `localStorage`, so an XSS would take the 8-hour session). The reset link is `/reset-password?token=…` (`mailer.py` `reset_link`) and the archive download is `…?token=…` (`archives.py`): both land in nginx's access log and the browser history. **Fix:** add the headers; put the reset token in the URL fragment or POST it; `access_log off` for the download location.

#### F-30 · One throttle key behind a load balancer
`nginx.conf` sends `X-Forwarded-For $remote_addr`; behind a cloud LB that address is the LB's, and uvicorn trusts every private range, so the per-address lock (50 failures) locks every user at once. Only matters for the ALB/Fly/Render deployments DEPLOY.md §3 describes. **Fix:** `real_ip_header` from the LB's range, as the nginx comment already suggests.

#### F-31 · Three sign-in-door details
`api/auth.py` `change_password` verifies `current_password` with no throttle (a token holder can guess the real password without limit). `forgot_password` looks the typed name up as a user row without checking it is a mailable address, so `admin` (the shipped `ORDERING_ADMIN_USERNAME`) queues a reset link — which signs its reader in as the admin — to the recipient string `admin`. `check_security_config` only logs when `ORDERING_JWT_SECRET` is the shipped default; compose refuses to start, a bare `uvicorn` does not — and the laptop's `.env` sets no secret, so it runs on the default today. **Fix:** throttle change-password per user; skip reset mail for rows without an `@`; refuse to start outside dev mode on a default secret.

#### F-32 · No drain on shutdown
`main.py` `lifespan` cancels only the sweeper and the backfill; a running order task is cancelled wherever it is awaiting. The reservation row written before the send keeps the record (so an order is never lost), but it stays `unconfirmed` and nobody finishes it; `docker compose up --build` or `uvicorn --reload` (the README's command) mid-run does this; `stop_grace_period` is the 10 s default. **Fix:** refuse new runs during shutdown, await in-flight runs for a grace period, set `stop_grace_period`, and never run real orders under `--reload`.

#### F-33 · No migration tool
`base.py` `sync_missing_columns` adds nullable columns and indexes only and says so; `compiled_archives.size` already needed a hand `ALTER`. Documented in DEPLOY.md §5; still a go-live item. **Fix:** Alembic before the first PostgreSQL deploy.

## Not confirmed / refuted
